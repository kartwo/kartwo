## 支付、发货与通知联动自动回归

新增隔离 HTTP 回归覆盖实际 Stripe 原始报文验签、异步付款入账、库存转实扣和确认信原子入队；错误签名/金额无副作用，重复回调不重复扣库或发信。实际本机 SMTP 协议测试覆盖 DATA 确认丢失后持久为“投递未知”、进程重启不自动重发、商家显式核对、运单更正以及部分/全额/迟到退款仍保留履约与通知证据、库存不自动回补。

这些测试只使用隔离 SQLite、运行时随机验签密钥、回环 SMTP 和 `.invalid` 虚构邮箱；不连接 Stripe 平台或外部邮件服务器。不能替代真实支付沙箱、SMTP TLS/服务商及顾客收件、常驻库人工验收。

## 基础售后开发边界

第一批范围已确认：退款申请和退货退款，换货由客服处理；商家审核后操作实际退款，不自动回补库存。售后核心、顾客原生表单、后台 HTTP 接口与 React/Ant Design 审核面板已接线；常驻验收服务已在完整备份后应用 0038。顾客从私密订单进入申请页，可申请、撤回或提交退回运单；未验证订单只显示原有邮箱验证页。申请不会自动触发退款、邮件或退货政策生成。

复用已有政策资料；未配置时不擅自采用演示默认退货期。现无签收记录及退回地址，不按发货日自动判定超期；退回说明和收货检查由商家明确处理。待审核申请阻止首次发货；金额、币种、订单均匹配且已验证的退款才能关联办结。界面验收继续复用常驻数据，资金操作只用沙箱。已有角色默认不增加处理权限；店主可审核，需要员工处理时由店主明确授权。

### 售后接口与表单契约

- 顾客：`GET /order/{id}/after-sales` 查看；`POST /order/{id}/after-sales` 申请；`POST /order/{id}/after-sales/{case}/actions` 撤回或保存退回运单。复用订单作用域 Cookie、严格同源、私密响应头、正文上限及 IP 限流；不读取 URL 中的草稿。
- 后台：`GET /admin/api/orders/{id}/after-sales` 返回绑定订单的有界 `snapshot` 和 UUIDv7 `next_action_key`；`POST /admin/api/orders/{id}/after-sales/{case}/actions` 接收 `request_key`、`expected_version`、`action`、顾客可见 `message` 和办结时的 `refund_request_id`。原键及原版本用于恢复同一动作，不能在未知结果时换键。
- 查看需订单与客户资料权限；处理另需独立 `orders.aftersales`，默认不给已有角色增权。该权限不包含退款网关或主密钥。角色编辑前后端均校验依赖，服务端还防御错误角色数据；员工、演示不能因此获得实际退款权限。
- 表单无 JavaScript 也可使用；成功 303 到干净路径，校验失败保留正文输入，冲突需明确重新核对。未知结果锁住新操作、保留原字段/键/版本供继续；业务或公共导航读取失败时保留独立恢复表单，不展示未确认记录。当前政策资料读取失败不阻止已有申请的查看/撤回。
- 金额按十进制字符串精确转整数分，并使用订单币种快照；店面私密订单金额展示同步改用原订单币种。申请、审核及退回记录独立于实际资金和库存，原动作重放不重复记业务事件或审核审计。私密 robots 元标签与 HTTP 头一致。

隔离自动检查覆盖真实邀请/登录/改权与 CSRF、演示/对象隔离、退回及检查过程、金额溢出/币种/URL 草稿拒绝、未知操作/数据库及导航失败恢复、正文及限流；原生浏览器用虚构订单和真实 CSP 验证一次失败后原请求恢复、退回批准与运单提交、390px 无横向溢出。临时入口/服务/标签在完成后移除，无真实邮件/资金或常驻数据写入。React 的隔离原生验收和常驻升级已完成；真实数据页面与适用人工、外部通道验收继续。

6. 编辑说明时检查普通刷新暂停，明确“刷新并保留说明”后内容还在；状态变化需主动采用新记录核对。缩窄窗口检查菜单、正文及弹窗，无整页横向溢出。异常恢复已由隔离自动测试覆盖；真实操作结果未知时继续原请求，勿另建退款。

## 整店恢复与临时访问隔离（2026-10-26）

恢复 ZIP 是恢复备份时点的数据，不能知道导出之后的退出、撤销或邀请消费事实。`kartwo restore` 现在在私有临时恢复目录内，先校验数据库，再同事务失效后台会话、员工邀请、顾客订单访问凭证与未用验证码；验证码正文清空，待发或发送中的旧验证码邮件取消。已发送/未知投递证据、原验证码限额时间保留，其他业务邮件保持原状态。复核清除结果成功后才原子落位；发生错误或静默未清除均不产生可用恢复目录，原数据和 ZIP 不变。兼容旧版备份中尚未存在的表，不执行迁移或创建新业务表。

恢复后店主用原账号密码登录，原加密配置仍可解锁；顾客重新验证邮箱后可继续原售后；未使用的员工邀请需重新生成。账号/角色和业务数据仍是备份时点，恢复不能代替对后来变动的权限与资金记录复核。同一店铺迁移切换前应停止旧实例。普通服务重启、原目录升级和常驻验收库不会触发此清除。

自动验证覆盖备份源与目标隔离、旧库兼容、正常/静默清除失败及异常授权表；实际后台导出 ZIP→新目录恢复→旧授权拒绝→原账号解密 SMTP 配置→顾客重新验证→原售后审核请求重放，确认原申请/政策/处理历史及媒体保留，审核事件和审计不重复、退款请求为零。SMTP 仅配置 `.invalid` 虚构地址，没有启动发信 worker，不连接外部服务。

最终恢复/实际HTTP流程竞态三轮通过（backup 15.621s、admin 20.791s），全仓 Go race 通过（admin 252.498s、order 66.238s、payment 75.079s、storefront 37.708s）；vet/lint 为零问题。CGO=0 最终二进制的实际 restore 命令已验证：43 张业务与配置表记录一致，原售后 approved/version2/2 事件及媒体保留，重复恢复拒绝覆盖，源数据库和 ZIP 的 SHA256 未变。最终 govulncheck 的可达代码及导入包漏洞为零，既有一个未导入模块告警保留，无豁免；密钥扫描通过。依赖和正式前端资源未修改。凭证隔离由 restore 命令执行，手工直接拷贝数据目录不会经过此步骤。

本批无需为人工验收清空或重建常驻库。仍用原账号在本机后台检查已有订单；只有进行恢复演练时才使用全新目录，原因是恢复命令必须拒绝覆盖已有店铺。CLI 新目录演练由开发端完成；实际支付、邮件和商家完整验收继续沿用各阶段指引。

### YouTube 来源策略与最终图文验证

原生检查实测 YouTube 错误 153。按 [Google 播放器来源要求](https://developers.google.com/youtube/terms/required-minimum-functionality)和 [Referrer Policy 的 strict-origin 定义](https://www.w3.org/TR/referrer-policy/#referrer-policy-strict-origin)，仅对已在白名单内的 YouTube iframe 使用 `strict-origin`：播放器获得站点 origin，不包含后台/文章路径、查询或片段。Vimeo 保持 `no-referrer`，页面、后台 API 和交易响应的隐私头不变；没有放宽 CSP 或播放器域名。服务端写入与读取、浏览器挂载/插入/保存均强制策略，文章输入属性不能覆盖；旧 HTML 读取时自动再过滤，不需迁移或批量改正文。

## B1 订单工作台（开发分支，2026-10-25）
